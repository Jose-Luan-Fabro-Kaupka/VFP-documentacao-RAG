# Considerações para criar novos tipos de saída de relatório

O modo de relatório assistido por objetos do Visual FoxPro 9 oferece potencial quase ilimitado para expandir seus horizontes de saída usando ReportListeners. O Report Output Application oferece um mecanismo conveniente para ajudá-lo a compartilhar suas extensões de relatório com outros usuários.

Este tópico fornece algumas diretrizes a considerar ao desenvolver e distribuir objetos de extensão do Report System.

# Decisões de design para extensões de relatório
 **Determine se seu objetivo é fornecer um novo tipo de resultado de saída não disponível no comportamento da classe base, como Rich Text, ou aprimorar vários formatos de saída, de maneira independente do resultado de saída.**
Se seu objetivo for aprimorar resultados de saída existentes, seu objeto provavelmente não precisa ser um ReportListener, e não é um Output Type. Projete esse objeto para ser suportável, como membro ou objeto auxiliar, por vários ReportListeners. Ele precisa ser de propósito único e pequeno, para eficiência. Projete um ReportListener para aceitar aprimoramentos iterando por uma coleção desses objetos. Por outro lado, se seu objetivo for um novo tipo de resultado de saída, ele deve ser um objeto derivado de ReportListener, para que possa fazer parceria com sucesso com o Report Engine. É um bom candidato para um mecanismo de cadeia de responsabilidade, conforme implementado pela ReportListener Base Foundation Class . Esse mecanismo permite gerar vários tipos de saída durante a mesma execução de relatório. Observação Você pode usar ambas as técnicas juntas. Registre seus objetos de aprimoramento em um único ReportListener e aplique seus efeitos à saída antes de enviar eventos aos Successors. Cada Successor pode decidir quais aprimoramentos são aplicáveis ao seu tipo de saída.
**Determine sua estratégia de tratamento de erros e publique os requisitos do seu objeto nesse aspecto.**
ReportListeners fazem parceria com o Report Engine de uma maneira exclusiva, devido à forma como processam código do usuário durante um único comando Visual FoxPro. Eles também podem fazer parceria com outro código do usuário em métodos DataEnvironment e funções definidas pelo usuário (UDFs) incorporadas no arquivo de relatório ou etiqueta. Há diferentes maneiras de tratar comandos REPORT FORM que não são concluídos corretamente. Consulte Handling Errors During Report Runs para obter informações e sugestões. Quando decidir uma estratégia, certifique-se de que os usuários da sua classe ReportListener tenham as informações adequadas para fornecer a limpeza adequada quando ocorrerem erros.
**Coloque tabelas temporárias exigidas pelo ReportListener na sessão especial fornecida para esse fim.**
A propriedade FRXDataSession do objeto ReportListener fornece as informações necessárias para acessar a cópia especial do arquivo de definição de relatório (.frx) durante a execução do relatório. Se seu ReportListener precisar trabalhar com cursors adicionais, use essa sessão protegida, em vez da sessão de dados que contém os dados nos quais o relatório se baseia, representada pela propriedade CurrentDataSession do objeto ReportListener . Essa estratégia garante que você deixe a sessão de dados "real" do usuário intacta e também garante a limpeza desses arquivos temporários ao término de uma execução de relatório. Cuidado Certifique-se de alternar adequadamente entre sessões de dados durante a execução do relatório, quando quiser usar a cópia do relatório ou seus outros arquivos de trabalho. Para obter mais informações, consulte SET DATASESSION Command . Dica Para um exemplo de relatório assistido por objetos que usa cursors adicionais em FRXDataSession, consulte Report XML MemberData Extensions .
**Faça uma distinção entre a propriedade OutputType e a propriedade ListenerType do ReportListener em seu design.**
OutputType fornece o valor com o qual o Report Output Application foi invocado, enquanto ListenerType representa o modo nativo de geração de saída fornecido pelo ReportListener da classe base. Uma classe derivada de ReportListener pode ser registrada para tratar muitos valores diferentes de OutputType na tabela de registro do Report Output Application, assim como o ReportListener da classe base suporta diferentes valores de ListenerType. No entanto, um OutputType também pode suportar comportamento de classe base e saída nativa diferentes, suportando vários valores de ListenerType.
