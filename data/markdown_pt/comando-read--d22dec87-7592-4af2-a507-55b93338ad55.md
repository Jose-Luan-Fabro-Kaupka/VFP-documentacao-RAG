# Comando READ

Incluído para compatibilidade com versões anteriores. Use o Form Designer.

Ativa objetos criados com os comandos @ ... GET e @ ... EDIT.

```foxpro
READ
	[CYCLE]
	[ACTIVATE expL1]
	[DEACTIVATE expL2]
	[MODAL]
	[WITH window title list]
	[SHOW expL3]
	[VALID expL4 | expN1]
	[WHEN expL5]
	[OBJECT expN2]
	[TIMEOUT expN3]
	[SAVE]
	[NOMOUSE]
	[LOCK | NOLOCK]
	[COLOR color pair list
	| COLOR SCHEME expN4]
```

# Observações

READ ativa objetos. Objetos são campos GET, caixas de seleção, listas, pop-ups, botões de pressão, botões de opção, spinners e regiões de edição de texto definidos com @ ... GETs. READ ativa todos os objetos criados após o último READ ou CLEAR GETS ter sido emitido.

Saindo do READ

 Um usuário pode sair de um READ de várias maneiras. Avançar além do último objeto ou retroceder além do primeiro objeto encerra o READ (se a cláusula CYCLE não estiver incluída com READ). Pressionar Escape, Ctrl+W ou escolher um controle definido para encerrar o READ também encerra o READ.

READ com várias janelas

 Um READ pode abranger várias janelas. Você pode colocar objetos em janelas diferentes e ativá-los todos com um único READ. Quando você move o cursor de objeto em objeto, os objetos são percorridos na ordem em que são criados, independentemente da janela em que estão colocados.

 Quando você move o cursor para um objeto, a janela que contém o objeto é ativada e se torna a janela de saída atual quando o objeto atual está na janela. Quando você pressiona Tab, Enter ou Down Arrow com o cursor posicionado no último objeto de uma janela, o cursor é posicionado no primeiro objeto da próxima janela. Quando você pressiona Shift+Tab ou Up Arrow com o cursor posicionado no primeiro objeto de uma janela, o cursor é posicionado no último objeto da janela anterior. SHOW GETS contém um exemplo de reads com várias janelas.

READs aninhados

 READs aninhados são criados definindo objetos e emitindo READ em uma rotina chamada enquanto um READ está ativo. Comandos READ podem ser aninhados até uma profundidade de cinco níveis. RDLEVEL() retorna o nível do READ atual. O tópico RDLEVEL() nesta ajuda online contém um exemplo com comandos READ aninhados.

Ordem de execução de eventos

 A lista a seguir mostra a ordem na qual eventos e cláusulas READ são executados quando o READ é emitido pela primeira vez:

  A cláusula WHEN no nível READ é executada

  A primeira janela GET é ativada

  A cláusula ACTIVATE no nível READ é executada

  A cláusula SHOW no nível READ é executada

  A cláusula WHEN no nível GET é executada para o primeiro GET

 A lista a seguir mostra a ordem na qual as cláusulas READ são chamadas quando uma nova janela é ativada:

  A cláusula VALID do campo sendo abandonado é executada

  A janela do campo sendo abandonado é desativada

  A janela do novo campo GET é ativada

  A cláusula DEACTIVATE no nível READ é executada

  A cláusula ACTIVATE no nível READ é executada

  A cláusula WHEN do novo campo é executada

CYCLE

 Se a cláusula CYCLE estiver incluída, o READ não é encerrado quando você avança além do último objeto ou retrocede além do primeiro objeto. Se o cursor estiver posicionado no último objeto e você pressionar Tab, Enter ou Down Arrow, o cursor é reposicionado no primeiro objeto. Se você estiver posicionado no primeiro objeto e pressionar Shift+Tab ou Up Arrow, será reposicionado no último objeto. Se CYCLE estiver incluído, pressionar um botão de encerramento, Escape, Ctrl+W ou emitir CLEAR READ ou uma cláusula TIMEOUT é necessário para encerrar o READ.

ACTIVATE expL1

 A cláusula ACTIVATE é executada quando READ é emitido e sempre que a janela READ atual mudar. ACTIVATE pode ser vista como uma cláusula WHEN no nível da janela.

 A expressão lógica expL1 é tipicamente uma função definida pelo usuário. WOUTPUT() pode ser usada na função definida pelo usuário para determinar qual janela é ativada. A função definida pelo usuário pode desabilitar objetos @ ... GET em outras janelas, ocultar janelas, exibir uma mensagem e assim por diante.

DEACTIVATE expL2

 A cláusula DEACTIVATE é executada sempre que você tenta trazer qualquer outra janela para frente (ou seja, sempre que WONTOP() mudar). DEACTIVATE pode ser vista como uma cláusula VALID no nível da janela.

 A expressão lógica expL2 é tipicamente uma função definida pelo usuário. A função definida pelo usuário pode ser usada para validar o conteúdo dos campos em uma janela antes de permitir que você traga outra janela para frente. O READ não é encerrado se a função definida pelo usuário retornar false (.F.). O READ é encerrado se a função definida pelo usuário retornar true (.T.).

MODAL

 Incluir a palavra-chave MODAL em READ impede que todas as janelas sejam ativadas, exceto as janelas envolvidas no READ. Se janelas que não estão envolvidas no READ estiverem definidas quando um READ MODAL é emitido, elas não podem ser ativadas ou acessadas.

WITH window title list

 Por padrão, todas as janelas interativas (janelas Browse, acessórios de mesa e janelas abertas com MODIFY FILE, MODIFY REPORT e assim por diante) podem participar de um READ. Inclua a cláusula WITH para restringir as janelas que participam do READ. The windows included in the WITH clause can include FoxPro system windows (Browse windows, desk accessories and text and memo editing windows).

 Including the WITH clause automatically creates a MODAL READ.

 Include the Browse window title (by default, the table alias) in the window list to make a Browse window accessible.

 Include the table alias in the window list to make a memo window accessible.

 If a window title contains a character that isn't alphabetic, numeric or an underscore, include the part of the title up to the first character that isn't alphabetic, numeric or an underscore in the window list. For example, if the window title is Client List, include Client in the window list (the space between Client and List isn't alphabetic, numeric or an underscore).

 If a window title contains a character that isn't alphabetic, numeric or an underscore, you can place the title in quotation marks in the window list. For example, if the window title is Client List, you can include "Client List" in the window list.

SHOW expL3

 A cláusula SHOW é executada sempre que SHOW GETS é emitido. O valor retornado por uma rotina SHOW é ignorado. Uma rotina SHOW pode ser usada para atualizar @ ... SAYs ou para habilitar ou desabilitar objetos.

VALID expL4 | expN1

 A cláusula VALID é avaliada quando você tenta sair do READ atual ou quando um READ emitido sem uma cláusula @ ... GET anterior expira por tempo. The VALID clause can specify a logical or numeric expression or a user-defined function (UDF) that returns a logical or numeric value.

 O READ é encerrado se expL4 for avaliada como true (.T.). Se VALID expL4 for avaliada como false (.F.) lógico, o objeto atual permanece ativo se possível.

 If the object cannot remain active (perhaps the VALID routine deactivated the object), you are moved to the first object.

 If the VALID clause returns a number, you are moved to the corresponding object. The READ is terminated if an object corresponding to the number doesn't exist. A VALID clause returning a value that isn't of logical or numeric type has the same effect as one returning true (.T.).

WHEN expL5

 A cláusula WHEN determina se o READ é executado. expL5 deve ser avaliada como true (.T.) quando o READ é emitido para que o READ seja executado. O READ é ignorado e a execução do programa continua com o comando imediatamente após o READ se expL5 for avaliada como false (.F.).

OBJECT expN2

 Inclua a cláusula OBJECT para especificar qual objeto é selecionado inicialmente quando READ é emitido. expN2 determines which object is initially selected. Object numbers are determined by the order in which the objects are created.

 Cada botão de pressão, de opção e invisível individual é considerado um objeto. In the following program example, a field and three radio buttons are created. The middle radio button is initially selected by including the OBJECT 3 clause with the READ. The NAME field is object number 1, the first radio button is object number 2, the second radio button is object number 3 and the last radio button is object number 4.

 STORE 1 TO radio

 STORE SPACE(10) TO name

 CLEAR

 @ 2,2 SAY 'Enter a name: ' GET name

 @ 4,2 GET radio PICTURE '@*R Apples;Oranges;Lemons'

 READ CYCLE OBJECT 3

TIMEOUT expN3

 Uma cláusula TIMEOUT determina por quanto tempo o READ permanece em vigor. expN3 specifies the number of seconds that can elapse without user input before the READ is terminated. Se o READ for encerrado por uma cláusula TIMEOUT, READKEY() retorna 20 se alterações não foram feitas em nenhum objeto. Se alterações foram feitas, READKEY() retorna 276.

 When READ is terminated by a TIMEOUT clause, any changes made to the field being edited when the READ ends are discarded. However, changes made to other fields are saved.

SAVE

 Todas as definições de objetos são automaticamente limpas quando o READ termina, a menos que a palavra-chave SAVE esteja incluída. Você pode reemitir READ sem recriar os objetos se incluir SAVE com o READ anterior.

NOMOUSE

 Inclua a palavra-chave NOMOUSE para impedir que objetos sejam selecionados com o mouse. Você deve usar o teclado para mover de objeto em objeto. Você ainda pode usar o mouse dentro dos campos para cortar, copiar, colar e posicionar o cursor.

LOCK | NOLOCK

 The LOCK and NOLOCK key words let you specify if a record containing fields specified in objects is automatically locked during a READ when the table is opened for shared use on a network.

 Se LOCK estiver incluído, bloqueios de registro são tentados para cada registro usado pelos objetos. If the locks are successfully placed, you can edit the records. SET REPROCESS determines how many times or for how long locking attempts are made. READ defaults to READ LOCK if LOCK or NOLOCK isn't included.

 Se NOLOCK estiver incluído, os registros usados pelos objetos não são bloqueados. Em vez disso, todos os objetos que usam campos nos registros são tornados somente leitura e o controle não pode ser selecionado e é exibido nas cores desabilitadas.

 Se você emitir READ NOLOCK e modificar um campo memo, o registro é automaticamente bloqueado.

COLOR color pair list

COLOR SCHEME expN4

 The color of the current @ ... GET editing region can be specified by including the number of an existing color scheme in the COLOR SCHEME clause or a set of color pairs in the COLOR clause.

 When an object is selected, it assumes the colors of the second color pair in the color pair list. All other colors in the color pair list are ignored. If you omit the first color pair you must include a comma for the color pair.

 If you include a COLOR SCHEME clause, color pair 2 of the specified color scheme determines the color of the current @ ... GET editing region. By default, the color of the current @ ... GET editing region is determined by color pair 2 of color scheme 1, color pair 2 of the window the @ ... GET editing region is placed in or color pair 2 of the color clause specified in @ ... GET. The color of other objects (check boxes, popups, push buttons, etc.) isn't affected by this color clause.

 Um esquema de cores é um conjunto de 10 pares de cores predefinidos. The color pairs in a color scheme can be changed with SET COLOR OF SCHEME. In FoxPro for MS-DOS the color pairs in a color scheme can also be changed in the Color Picker.

 Um par de cores é um conjunto de duas letras separadas por uma barra. A primeira letra de cor especifica a cor de primeiro plano e a segunda letra especifica a cor de fundo.

 Por exemplo, este par de cores especifica um primeiro plano vermelho em um fundo branco:

 R/W

 Para uma lista de cores e suas letras de cor correspondentes, consulte os comandos SET COLOR e o tópico Color Table by Color Pair nesta ajuda online.

 A color pair can also be specified with a set of 6 RGB (Red Green Blue) color values separated by commas. The first 3 color values specify the foreground color and the second 3 color values specify the background color. The color values can range from 0 through 255.

 The R/W color pair in the example above can also be specified with this RGB color pair:

 RGB(255,0,0,255,255,255)

READ de fundação

 O FoxPro permite criar facilmente interfaces orientadas a eventos (como a interface do FoxPro) para suas aplicações. This section suggests a method for creating an event-driven interface in FoxPro.

 Em versões anteriores do FoxPro, alguns usuários sofisticados utilizavam um loop de eventos para tratar escolhas de menu e seleções de janela ao criar uma interface orientada a eventos. The event loop would constantly poll the system status and then take action based on which window was on top or which menu option the user chose.

 DO WHILE é usado para criar o loop de eventos (frequentemente um loop grande). Loops de eventos devem ser evitados pelos seguintes motivos:

  Loops de eventos estão constantemente sendo executados, tornando-os intensivos no uso de CPU.

  Loops de eventos são complexos e difíceis de programar.

  Loops de eventos são inadequados em ambientes multiprograma como DESQview, Windows e o Macintosh MultiFinder.

Um único READ com várias janelas

 Programação com loop de eventos raramente é necessária no FoxPro. Um único READ que suporta várias janelas pode ser usado para eliminar a maioria dos loops de eventos. A single READ with multiple windows provides versatility and flexibility without complex programming.

 Sugerimos que você englobe todas as janelas com as quais pretende interagir. FoxPro can coordinate windows containing objects (@ ... GETs, check boxes, radio buttons, popups, and so on) with other windows not usually associated with a READ. By default, all interactive windows (Browse windows, desk accessories, memo editing windows and windows opened with MODIFY FILE, MODIFY REPORT) can participate in a READ.

Coordenando janelas com um único READ

 To programmatically coordinate windows containing @ ... GET objects with a single READ:

  Create the windows that will contain the @ ... GET objects.

  Activate one of the windows and issue the @ ... GETs that create the objects for the window.

  Activate another window and issue the @ ... GETs that create the objects for that window.

  Continue in this fashion for the remaining windows.

  Issue READ.

 O código de programa de conjunto de telas gerado por GENSCRN fornece um bom exemplo desta sequência.

 The windows created and activated are now coordinated with a single READ. Each of the GET objects appears in its respective window, and the user can move between the @ ... GET objects in each of the windows. When the user moves from object to object with the keyboard, the objects are traversed in the order the @ ... GETs have been issued, regardless of which window they are in. A window is activated and becomes the current output window when the current object is in the window.

 When the user presses Tab, Enter or Down Arrow when the cursor is positioned on the last object in a window, the cursor is positioned on the first @ ... GET object in the next window. When the user presses Shift+Tab or Up Arrow on the first object in a window, the cursor is positioned on the last @ ... GET object in the previous window. The user can also move between different @ ... GET objects in different windows by clicking on the objects.

 Access to other windows during a single READ can be controlled with the READ MODAL clause. Including MODAL in READ prevents interaction with windows that are not encompassed in the READ's coordinated set of windows. When MODAL is included with READ, the user cannot close, zoom, minimize, or move windows not involved in the READ. Clicking on a window not involved in the READ sounds a beep if BELL is SET ON.

 By default, all interactive windows (Browse windows, desk accessories and windows opened with MODIFY FILE, MODIFY REPORT, and so on) can participate in a READ.

 You can explicitly indicate the windows that participate in the READ by specifying their names in the WITH clause. The READ command is automatically made MODAL if you include the WITH clause to specify other windows involved in the READ. The windows included in the WITH clause can include FoxPro system windows (Browse windows, desk accessories and text and memo editing windows).

ACTIVATE e DEACTIVATE

 When a window involved in the READ is brought forward, the action taken can be controlled by the ACTIVATE e DEACTIVATE clauses. The user can bring a window forward by clicking on the window, by cycling to the window with Ctrl+F1 or by choosing a control or menu option that activates the window.

 When a window containing objects is foremost and you attempt to bring another window forward, the DEACTIVATE clause is executed after the new window is brought forward.

 The value returned by the DEACTIVATE clause determines whether the READ is terminated If the DEACTIVATE clause returns true (.T.), the READ is terminated. If the clause returns false (.F.), the READ isn't terminated.

 When the DEACTIVATE clause is executed, WONTOP() returns the name of the new window brought forward and WLAST() returns the name of the window that was formerly frontmost. The window functions (WONTOP(), WOUTPUT() ...) return false (.F.) when you include the name of a window that doesn't exist.

 If your DEACTIVATE clause lets the new window remain forward and the new window contains objects, the ACTIVATE clause is executed.

 HOT TIP 

 Quando uma janela é trazida para frente, você pode retornar a janela à sua posição anterior emitindo o seguinte comando na cláusula DEACTIVATE:

 ACTIVATE WINDOW (WLAST())

 A função WREAD() facilita a manipulação de janelas que participam de um READ. WREAD() lets you determine if a specific window is participating in the current READ.

Coordinating Multiple READs / READ de fundaçãos

 The single READ with multiple windows section above recommends an approach to handling multiple windows with a single READ command. The single READ approach works for most applications.

 However, a foundation READ may be necessary in some applications. Um READ de fundação é um READ sem objetos. A foundation READ is used to coordinate multiple READs into a single interactive session.

 Um READ de fundação tipicamente incorpora código em sua rotina de cláusula VALID que ativa e controla os READs filhos. Child READs are sometimes called nested READs.

 A foundation READ normally has a VALID clause. The VALID clause is executed when an event occurs that would otherwise terminate the READ. Here are the events that terminate a foundation READ:

  Any mouse click or keystroke that isn't a menu selection or doesn't execute an ON KEY LABEL. During a foundation READ, the FoxPro system menu is accessible.

  Selecting an item from a menu or executing an ON KEY LABEL command doesn't terminate a foundation READ. If a menu is activated but a selection isn't made from the menu, the foundation READ isn't terminated.

  A child READ is terminated. However, the foundation READ isn't terminated if a grandchild READ is terminated.

 The value returned by the READ VALID clause determines whether or not the foundation READ is terminated. If the READ VALID clause returns true (.T.), the foundation READ is terminated; if it returns false (.F.), the foundation READ command remains active.

 READKEY() facilita o gerenciamento de comandos READ filhos. By specifying a numeric argument in READKEY(), you can determine how the last READ was terminated. For example, the value can indicate that the last READ was terminated by closing a window, by a CLEAR READ, by a READ VALID or DEACTIVATE clause returning a logical true (.T.).

 Here are the values returned by READKEY(expN) with the corresponding reason the READ was terminated:

 Valor Motivo

 ----- ------

 1 Nenhum dos seguintes

 2 CLEAR READ emitido

 3 Controle de encerramento escolhido

 4 Janela READ fechada

 5 Cláusula DEACTIVATE retornou .T.

 6 READ expirou por tempo

Aplicações de exemplo

 Incluídas com o FoxPro estão três aplicações de exemplo, INV.APP, EX1.APP e EX2.APP. Essas aplicações de exemplo ilustram os recursos disponíveis com READs e como esses recursos podem ser usados para criar uma interface orientada a eventos.

 The applications are built from three projects, INV.PJX, EX1.PJX and EX2.PJX. The projects contain all the files (programs, screen sets, menus, tables, and so on) used by the applications. To examine the files included in a project, open the project with MODIFY PROJECT, or through the Open dialog.

INV: Um único READ com várias janelas

 The sample application INV.APP demonstrates the use of a single READ with multiple windows. A user-defined window containing @ ... GET objects, two Browse windows and the CONTROL2 screen set control panel are coordinated with a single READ command.

EX1: Um READ de fundação com várias aplicações

 EX1.APP, a more complex application than INV.APP, demonstrates coordination of four READs, each of which use the control panel built from the CONTROL3.SCX screen set. A foundation READ coordinates the four READs. EX1.APP has been designed so you can utilize any FoxPro desk accessories or windows (Help, Filer, Calculator, Calendar/Diary, editing windows, and so on) in conjunction with the application windows.

 Applications are launched from the Application menu. You can switch from one application to another by clicking in the respective application window. Execution of the entire system can be terminated by choosing the Quit option in the File menu.

EX2: Um READ de fundação com várias aplicações

Questionário EX1 Answers

 1. You would add one READ level each time you selected an application from the menu and, therefore, would get "Too many READs in effect" in short order. FoxPro supports a maximum of five READ levels.

 2. Because the procedure MENUHIT is contained within EX1.MPR. EX1.MPR isn't a part of EX1.PRG; the IN EX1.MPR clause must be included to tell EX1.PRG where to look for the MENUHIT procedure.

 3. It's found in the STOPREAD procedure which is evaluated each time an application window is deactivated. The window name is passed to STOPREAD. If the window isn't visible, (because it was closed either manually or by clicking on its close box) the control panel is displayed. STOPREAD returns .T. if the window is involved in the READ, otherwise .F. is returned (a FoxPro system window was closed).

 4. There are at most three READs active: the foundation READ, one of the application READs, and a READ MODAL associated with either BROWSER.SPR or FINDER.SPR.

 5. The procedure named EFFACE, which is called in the cleanup code for each application screen, ensures that when the last application window is closed the control panel is released.

 EFFACE is called when either the Quit button is pressed or a READ window has been manually closed.

 EFFACE looks through all the windows that are open, from back to front. If it finds any of the user application windows (which require the control panel) it simply exits. Otherwise, it concludes you're finished with the control panel and releases it.

 6. The application READ is terminated because its Cláusula DEACTIVATE retornou .T., but the foundation READ remains active.

 7. The first application's DEACTIVATE clause returns .T., thereby terminating that application's READ. Termination of the application's READ triggers the foundation READ's VALID clause routine.

 8. This routine, called MYHANDLER, uses WONTOP() to return the name of the application window where the mouse was clicked, and the screen program (.SPR) for that window is executed.
